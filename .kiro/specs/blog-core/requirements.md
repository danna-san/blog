# 要件定義: blog-core（Issue から書く日記ブログの基本機能）

書式は EARS（「〜のとき、システムは〜する」）。ID は変更せず、削除する場合も欠番として残す。

## 用語

- **書き手**: `blog.config.json` の `publish.allowedAuthors` に含まれる GitHub ユーザー。空ならリポジトリ所有者だけ。
- **投稿 Issue**: 書き手が作った Issue のうち、タイトルが `/` で始まらず、`skipLabels`（既定: `draft`, `no-blog`）が付いていないもの。
- **素材**: 投稿 Issue の本文と、そこへの書き手のコメント。1 つ 1 つが記事の「出来事」1 件になる。
- **日記上の日付**: タイムゾーン（既定 `Asia/Tokyo`）で `dayStartHour`（既定 4）時を日付の区切りとした日付。
- **公開済み**: `publishedLabel`（既定 `published`）が付いた Issue。

---

## R1 投稿の収集

- R1.1 システムは、書き手以外が作った Issue とコメントを、記事の素材にもプロンプトにも含めない。
- R1.2 システムは、Pull Request、タイトルが `/` で始まる Issue、`skipLabels` が付いた Issue を素材にしない。
- R1.3 書き手のコメントが `/publish` で始まるとき、システムはそのコメントを素材にしない。
- R1.4 システムは、閉じられた Issue のうち公開済みラベルが無いもの（書き手が手で閉じたもの）を素材にしない。

## R2 日付の決定

- R2.1 素材の日付は、その素材の作成日時の「日記上の日付」とする（例: 1:30 の投稿は前日扱い）。
- R2.2 コメントの日付は、日付指定（R2.3）が無ければ、元の Issue の日付とする（翌日以降のコメントも元の Issue の日に入る）。
- R2.3 Issue 本文またはコメント本文の 1 行目が日付指定のとき、システムはその素材の日時を指定された日時とし、指定行は本文から取り除く。日付指定の書式は次のとおり。
  - 日付: `@2026-11-05` / `@11/5` / `@昨日` / `@一昨日` / `@3日前`
  - 時刻（任意。日付の後に空白で続ける）: `18:30` / `18時` / `18時30分`
  - 時刻だけ（日付を省略）: `@18:30` / `@21時`（R2.9）
  - 例: `@11/5 18:30`、`@一昨日`、`@昨日 21時`、`@21時`
- R2.4 `@11/5` のように年を省略したとき、システムは素材の作成日以前で最も近いその月日とする。
- R2.5 「昨日」「一昨日」「N日前」は、素材の作成日時の日記上の日付から数える。
- R2.6 日付指定で時刻を省略したとき、システムはその素材をその日の最後に「追記」として置く。
- R2.7 日付指定が素材の作成日より未来の日付を指すとき、または解釈できないとき、システムは日付指定を無視して通常どおり扱い、ログに警告を出す。
- R2.9 日付を省略して時刻だけを指定したとき、システムは、Issue 本文ならその Issue の投稿日（日記上の日付）、コメントなら元の Issue の日付に、その時刻を当てる。
- R2.10 区切り時刻（4 時）より前の時刻、または 24〜29 時の指定は、その日の深夜（暦の上では翌日）として扱い、日記上の日付は変えない。
- R2.8 記事上の時刻表示は、指定時刻または作成時刻（HH:MM）とする。素材の実際の日付が記事の日付と異なり、かつ時刻指定が無いときは、時刻の代わりに「追記」と表示する。

## R3 実行のきっかけ

- R3.1 毎日 6:00（JST）に、システムは前日までの未公開の投稿 Issue を日付ごとに記事にする（当日分は含めない）。
- R3.2 書き手が任意の Issue に `/publish` とコメントしたとき、システムは当日分も含めて未公開の投稿 Issue を記事にする。
- R3.3 書き手が `/publish YYYY-MM-DD` とコメントしたとき、システムはその日の記事を、公開済みを含むその日の全素材から作り直す。
- R3.4 未公開の素材がすでに記事のある日付に属するとき（日付指定による過去への追記、公開後のコメント追加など）、システムはその日の記事を、その日の全素材から作り直す。
- R3.5 GitHub の Actions 画面からの手動実行（日付指定・当日分を含めるかの指定つき）でも、R3.2 / R3.3 と同じ処理ができる。
- R3.6 同時に複数の公開処理が走らないようにする。

## R4 記事の構成

- R4.1 1 日 1 記事とし、URL は `<baseUrl>/YYYY-MM-DD.html` とする。
- R4.2 記事には、その日の全素材を時刻順に「出来事」として並べる。各出来事には時刻（または「追記」）を表示する。
- R4.3 素材に添付された画像・動画は、素材の中で添付されていた位置の近くに、すべて表示する。抜け落ちた画像は、その出来事の末尾に置く。
- R4.4 記事のタグは、投稿 Issue のラベル（システム用ラベルを除く）と、本文・タイトル中の `#タグ`（数字だけのものは Issue 参照なので除く）を合わせたものとする。`#タグ` は本文から取り除く。
- R4.5 記事には、タイトル、日付（曜日つき）、タグ、出来事の並び、締めのひとこと（素材に根拠がある場合のみ）、前後の日記へのリンクを表示する。

## R5 文章の生成

- R5.1 システムは、`config/persona.md`（文体の質問票）、`config/samples/`（任意の文章サンプル）、`ai.rewriteLevel` に従って、書き手本人が書いたような文章にする。
- R5.2 システムは、素材に無い出来事・人物・場所・感想を足さず、写真の内容を想像で描写しない。固有名詞・数字・本人の言葉は残す。
- R5.3 本文に時刻（「10時23分に」等）を書かない（時刻は別に表示するため）。
- R5.4 箇条書き、Markdown 見出し、読者への呼びかけ、まとめや教訓での締めを使わない。
- R5.5 Claude で生成するとき、システムは下書きを yomiyasu（文書の種類はエッセイ）で推敲してから出力する。
- R5.6 生成結果に `config/banned-phrases.txt` の言い回しが含まれるとき、システムは書き直しを求める（API 生成時は 1 回まで再依頼。Claude 生成時は依頼内で自己点検させ、残った場合はログに警告）。
- R5.7 生成結果の出来事が素材と対応しない（欠けている・余計な ID）とき、欠けた出来事は素材の文章を整形して使い、余計なものは捨てる。

## R6 失敗時の扱い

- R6.1 Claude での生成が失敗した日（応答なし・JSON として読めない等）は、GitHub Models で生成する。
- R6.2 GitHub Models でも失敗した日は、その日の記事を公開せず、その日の Issue を開いたまま残す。ジョブは失敗として終了させ、GitHub の通知で書き手に知らせる。
- R6.3 一部の日だけ失敗したとき、成功した日の記事は公開する。
- R6.4 画像のダウンロードや変換に失敗したとき、記事の公開は止めず、元の添付 URL を参照する。

## R7 メディア

- R7.1 システムは添付の画像・動画を `docs/assets/media/YYYY/MM/` に保存し、記事からはそれを参照する。同じ添付は 2 回ダウンロードしない。
- R7.2 画像は長辺 `images.maxWidth`（既定 1600px）以下に縮小し、向きを正しく直してから、位置情報を含むメタデータを消す。ImageMagick が無い環境では、JPEG の GPS 情報だけを消す。
- R7.3 GIF は縮小しない（アニメーションを壊さないため）。
- R7.4 `images.maxVideoMB`（既定 25MB）を超える動画は保存せず、元の添付 URL を参照する。
- R7.5 画像には幅・高さを指定し、遅延読み込みにする。

## R8 公開後の処理

- R8.1 記事を公開（push 成功）した後、システムはその記事に含めた未公開の Issue に公開済みラベルを付けて閉じる。
- R8.2 システムは Issue に自動コメントを残さない。
- R8.3 自動コミットの作者は書き手本人の名前と GitHub の noreply アドレスとし、コミットメッセージは「11/7 の日記」のような普通の文にする。
- R8.4 push に失敗したとき、システムは Issue を閉じない。

## R9 サイトの構成

- R9.1 全ページ共通で、ヘッダー、ヘッダー下のタグ一覧（記事数の多い順に `ui.headerTagCount` 件）、左メニュー、コンテンツ領域、フッターを持つ。
- R9.2 左メニューには、全記事への年 → 月 → 日の折りたたみリンクを表示する。表示中の記事の年月は開き、その日は強調する。
- R9.3 タグ一覧・左メニュー・前後リンクは、単一の JSON（`docs/data/index.json`）から JavaScript で描画する。記事を追加しても既存の記事 HTML は書き換えない。
- R9.4 タグページ（`tags.html?tag=名前`）は 1 枚の HTML とし、JSON から該当記事を一覧する。タグ一覧と、タイトル・紹介文のキーワード絞り込みも置く。
- R9.5 トップページには最新 `ui.indexPostCount` 件の記事カード、全記事一覧ページ（`archive.html`）には年月ごとの一覧を、静的 HTML で出す（JavaScript が無くてもたどれるように）。
- R9.6 Atom フィード（`feed.xml`）、`sitemap.xml`、`404.html` を出力する。
- R9.7 各ページに OGP（タイトル・説明・最初の画像）と canonical を出力する。

## R10 デザインと操作

- R10.1 `templates/layout.html` は、ブラウザで直接開くとサンプル記事入りでデザインを確認できる。
- R10.2 スマホ幅では左メニューをボタンで開閉するドロワーにする。Esc とオーバーレイのクリックで閉じる。
- R10.3 スクロールに合わせたフェードイン、画像のライトボックス（矢印キー・Esc 対応）、トップへ戻るボタンを、ライブラリなしで実装する。
- R10.4 `prefers-reduced-motion` のときはアニメーションを止める。
- R10.5 OS の設定に合わせたダークモードと、手動の切り替えボタンを持つ（選択はブラウザに保存）。
- R10.6 JavaScript が無効でも、記事本文・トップ・全記事一覧は読める。

## R11 作り直し

- R11.1 テンプレート・CSS・JS・設定・`content/posts/*.json` が変更されて push されたとき、システムは AI を呼ばずに全ページを作り直す。
- R11.2 CSS / JS の URL には内容のハッシュを付け、変更がすぐ反映されるようにする。
- R11.3 `content/posts/*.json` を手で直して push すれば、記事の誤字などを直せる。

## R12 セキュリティ

- R12.1 秘密情報は GitHub Secrets にだけ置き、リポジトリのファイルとログに出さない。
- R12.2 Claude に許可するツールは Read、Write、Skill（yomiyasu の呼び出し）、yomiyasu の lint スクリプトの実行だけとする。
- R12.3 `/publish` コメントによる実行は、書き手のコメントのときだけ行う（ワークフローとスクリプトの二重確認）。
- R12.4 外部入力（Issue のタイトル・本文・コメント）をワークフローのシェルに直接埋め込まない。
- R12.5 利用する Actions はコミット SHA で固定する。
- R12.6 npm パッケージ、ブラウザ用ライブラリ、CDN、Web フォントを使わない。
- R12.7 HTML 生成時はすべてエスケープし、ブラウザ側で `innerHTML` にデータを入れない。

## R13 フォークしやすさ

- R13.1 `npm run reset-content` で、記事データ・生成ページ・メディアを消し、空のブログに戻せる。
- R13.2 ブログ名・URL・書き手・タイムゾーン・AI 設定は `blog.config.json`、文体は `config/`、見た目は `templates/` と `docs/assets/` だけで変えられる。
- R13.3 README に、フォークからの初期設定（Pages、Secrets、Actions の権限、トークン発行）を手順として書く。

## R14 開発の進め方

- R14.1 機能の追加・変更は、`.kiro/specs/<機能名>/` に requirements → design → tasks を書き、書き手の承認を得てから実装する。
- R14.2 全体方針が変わるときは `.kiro/steering/` を更新する。
